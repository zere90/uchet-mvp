# Учётная система — MVP «Поступление запасов»

Первый рабочий контур учётной системы для госучреждений: от накладной поставщика
до остатков на складе и бухгалтерских проводок. Требования описаны в PRD
«Первый рабочий контур учётной системы: поступление запасов» (версия 0.1).

**Стек:** Python 3.11+, FastAPI, PostgreSQL 16, psycopg 3, pytest.

## Как устроено

Одно событие («поставщик привёз товар») записывается в три слоя:

| Слой | Таблицы | Отвечает на вопрос |
|---|---|---|
| 1. Документ | `doc_goods_receipt`, `doc_goods_receipt_line` | что произошло |
| 2. Регистры | `reg_stock`, `reg_settlement`, `reg_price` | сколько чего у нас |
| 3. Проводки | `acc_entry` | сходится ли баланс |

Регистры и проводки заполняются только при проведении документа, по правилам из
таблицы `meta_posting_rule`. Правила — это данные, а не код: номера счетов в коде
не встречаются.


## Запуск

1. **PostgreSQL.** Проще всего через Docker:
   ```bash
   docker compose up -d
   ```
   Создадутся две базы: `uchet` (рабочая) и `uchet_test` (для тестов).
   Без Docker можно поставить [Postgres.app](https://postgresapp.com) и создать базы
   `uchet` и `uchet_test` вручную.

2. **Python-окружение:**
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate          # Windows: .venv\Scripts\activate
   pip install -r requirements.txt
   cp .env.example .env
   ```

3. **База:** создать таблицы и загрузить тестовые данные
   ```bash
   python scripts/init_db.py
   ```

4. **Сервер:**
   ```bash
   uvicorn app.main:app --reload
   ```
   Документация API с кнопками «попробовать»: http://localhost:8000/docs

5. **Тесты:**
   ```bash
   pytest -v
   ```

## API справочников (этап 1)

Восемь справочников: `organizations`, `counterparties`, `contracts`, `units`,
`items`, `warehouses`, `persons`, `accounts`.

```
GET   /api/v1/catalogs/{справочник}?q=&page=&include_deleted=   список, поиск по коду и наименованию
GET   /api/v1/catalogs/{справочник}/{id}                         один элемент
POST  /api/v1/catalogs/{справочник}                              создать            → 201
PUT   /api/v1/catalogs/{справочник}/{id}                         изменить           → 200
POST  /api/v1/catalogs/{справочник}/{id}/deletion-mark           пометка на удаление → 200
```

Физического удаления нет — только пометка. Ошибки возвращаются в формате PRD:

```json
{
  "error": "validation_failed",
  "message": "Данные не сохранены",
  "details": [{ "field": "code", "code": "duplicate", "message": "Такое значение уже есть в справочнике" }]
}
```

## API документа «Поступление запасов» (этап 3)

Префикс: `/api/v1/documents/goods-receipt`.

| Метод и путь | Результат |
|---|---|
| `POST ""` | Создать черновик, ответ 201 |
| `GET ""` | Список по 50 документов на странице |
| `GET /{id}` | Шапка и строки с наименованиями справочников |
| `PUT /{id}` | Изменить черновик, полностью заменить строки |
| `POST /{id}/post` | Провести и вернуть документ с `record_counts` |
| `POST /{id}/unpost` | Отменить проведение и вернуть документ |
| `GET /{id}/records` | Движения трёх регистров и бухгалтерские проводки |
| `POST /{id}/deletion-mark` | Установить или снять пометку: `{"mark": true}` / `{"mark": false}` |

Пример тела создания и изменения:

```json
{
  "doc_date": "2026-09-14T10:00:00+05:00",
  "org_id": "00000000-0000-0000-0000-000000000001",
  "counterparty_id": "00000000-0000-0000-0000-000000000101",
  "contract_id": "00000000-0000-0000-0000-000000000201",
  "warehouse_id": "00000000-0000-0000-0000-000000000301",
  "mol_id": "00000000-0000-0000-0000-000000000401",
  "supplier_doc_no": "47",
  "supplier_doc_date": "2026-09-14",
  "lines": [
    {"item_id": "00000000-0000-0000-0000-000000000601", "qty": "40", "price": "1850"},
    {"item_id": "00000000-0000-0000-0000-000000000602", "qty": "6", "price": "22500"},
    {"item_id": "00000000-0000-0000-0000-000000000603", "qty": "200", "price": "190"}
  ]
}
```

Сервер выдаёт номер, берёт единицы измерения из номенклатуры, округляет каждую
сумму строки до двух знаков (`ROUND_HALF_UP`) и складывает их. В примере итог —
`"247000.00"`. Поля `amount`, `amount_total`, `number` и `status`, присланные клиентом,
игнорируются. В ответах денежные значения и количества передаются строками,
чтобы сохранить точность `Decimal`. Количество допускает до трёх знаков после
запятой, цена — до двух.

`doc_date` по умолчанию равна текущему времени. Дата без часового пояса считается
местной (`Asia/Almaty`), в базе и ответах используется UTC. Год для выдачи номера
определяется по дате документа в `Asia/Almaty`. Договор, МОЛ и реквизиты накладной
поставщика необязательны. Можно сохранить пустой черновик, но провести его нельзя.
Если `price` отсутствует или равна `null`, выбирается последняя цена этого
поставщика и товара не позднее даты документа. При отсутствии истории — 422
«Укажите цену в строке N». Нулевая цена допустима.

Список принимает `page`, `q` (номер или название поставщика), `status`
(`draft`, `posted`, `deleted`), `org_id`, `date_from`, `date_to`, `include_deleted`.
Границы дат задаются как `YYYY-MM-DD` и включают указанные дни в `Asia/Almaty`.
Формат ответа: `{items, total, page, page_size}`. Помеченные документы скрыты,
пока не указан `include_deleted=true`.

Наименования в ответах находятся в полях `org_name`, `counterparty_name`,
`contract_name`, `warehouse_name`, `mol_name`, а в строках — `item_name`, `uom_name`.
`POST /{id}/post` возвращает ту же шапку и строки, дополнив их полем:

```json
{"record_counts": {"reg_stock": 3, "reg_settlement": 1, "reg_price": 3, "acc_entry": 3}}
```

`GET /{id}/records` возвращает массивы с этими четырьмя ключами. В движениях
добавлены названия справочников; в проводках — `dt_account_name`, `kt_account_name`
и расшифровки аналитики `dt_dims_names`, `kt_dims_names`.

Номер, год нумерации `number_year` и организация при изменении сохраняются.
Уникальность номера проверяется в пределах организации и года по `Asia/Almaty`.
Перенос даты в другой год отклоняется с 422 (`doc_date`, `year_change`). Правка проведённого документа
даёт 409 `document_posted`, помеченного — 409 `document_deleted`.
Ошибки проведения — 422 `posting_failed`, отсутствующий документ — 404 `not_found`.
Для проведённого документа пометка удаляет движения через отмену проведения;
для черновика лишнее действие `unpost` в аудит не добавляется. Снятие пометки возвращает
черновик. Физического удаления нет. Создание, изменение, проведение, отмена и
пометки записываются в аудит с `DEV_USER_ID`. Изменения и аудит сохраняются
в одной транзакции; неудачная операция откатывается вместе с выданным номером.

## Допущения на текущем этапе

- **Аутентификации пока нет.** В PRD предусмотрен вход через OIDC; до его подключения
  все действия пишутся в журнал от имени `DEV_USER_ID` из `.env`.
- **Номера счетов в `seed.sql` — иллюстрация из PRD.** Точные субсчета нужно сверить
  с приказом Министра финансов РК от 16.04.2025 № 170.
- **Нумерация документов — отдельная по организации и году** (как в FR-03). Открытый
  вопрос PRD о сквозной нумерации по всей базе решается правкой одной функции
  `next_doc_number`.
